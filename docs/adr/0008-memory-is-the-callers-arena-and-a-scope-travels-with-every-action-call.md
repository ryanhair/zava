# Memory is the caller's arena; a scope travels with every action call

Every action call takes a scope: a kernel-defined value the caller builds from an allocator and a `std.Io`, passed explicitly beside the context to the action and to every function step. Everything an action returns is allocated in the scope's allocator and is never freed piece by piece: no record, slice or result has a `deinit`, and the caller releases all of it at once, so the allocator is expected to behave like an arena. Working memory lives in a scratch arena owned by the outermost action call and released when that call returns. We chose this because it keeps records plain values, puts exactly one copy between a driver row and the caller, and gives the open transaction a visible path through nested action calls with no hidden state.

## Considered Options

- **A result that owns its memory** (a wrapper with its own arena and a `deinit`, the shape pg.zig uses): rejected because every read would return a wrapper instead of a slice of records, and every caller would carry a `defer` for memory that a request arena already frees.
- **A generated `deinit` per record** that walks every slice: rejected because it lets records be freed one at a time, which nothing asked for, at the price of a free per text value and a rule about which records are owned and which are borrowed.
- **Thread-local state** for the allocator and the open transaction: rejected because it hides what a call depends on, breaks when work moves between threads, and is not how Zig code is written.
- **The allocator and transaction as fields of the context**: rejected because the kernel gives the context's fields no meaning (ADR 0005). The context is the developer's data; the scope is the kernel's.
- **The scope holding the context**, so that calls take one parameter: rejected because a nested call made under a different context would need a way to derive a scope, where two parameters need nothing.
- **Scratch in the caller's allocator with the results**: rejected because a long-running caller, such as a job loop, would grow by the working memory of every call.
- **Scratch released when each action call returns**: not possible. A nested action's after-commit steps wait for the outermost commit and still read that action's draft.

## Consequences

- An action call is spelled `Author.register(scope, context, input)`. Every function step gains the scope as a parameter before the context; the signatures recorded with ADR 0005 change accordingly.
- A scope is built once per unit of work (a request, a job, a test) and may be used for any number of top-level action calls in sequence. At rest it owns nothing, so it has no `deinit`.
- The scope carries the open transaction opaquely, one slot per data layer in the domain. A step that calls another action passes its scope on, and that is how the nested action joins the transaction. The kernel never shows the transaction to the developer. A data layer may publish an accessor for it; the Postgres data layer does, returning the connection inside the current transaction, so that hand-written SQL in a generic action takes part in it. Rows read through that connection are the developer's responsibility and fall outside the rule that no driver memory leaves the data layer.
- The data layer decodes each value from the borrowed driver row straight into the scope's allocator. Nothing is copied twice and nothing the driver owns is returned.
- The scratch arena is backed by the scope's allocator, shared by nested calls, and released after the outermost call's after-commit steps. It holds the draft, encoded parameters, accumulated validation failures, the current record, and anything a change allocates. Once a call returns, what remains allocated is its result and nothing else.
- A step sees both allocators, named by lifetime: `scope.scratch` and `scope.allocator`. A value a change puts in the draft comes from scratch, since the stored record is decoded afresh. A value a generic action returns comes from the scope's allocator. Returning scratch memory is a bug the compiler cannot catch; debug builds poison scratch on release so that it fails loudly.
- Input is borrowed for the duration of the call and never kept. A returned record never aliases the input, the draft or scratch. The stored record that after and after-commit steps receive is the one the caller receives.
- On failure, the failure detail is allocated in the scope's allocator, because it outlives scratch. Results allocated before the failure are not unwound; they go when the caller resets its allocator.
- Passing a general-purpose allocator leaks. This is the documented cost of the contract, and the documentation says to pass an arena.
- The kernel has no arena of its own and no per-request convention. The server-agnostic HTTP handler takes an allocator from whoever mounts it; the http.zig binding builds a scope per request from http.zig's request arena. A developer calling actions directly chooses their own.
- One action call runs on one thread from start to finish. The scope, the draft, the transaction and scratch never cross threads; an after-commit step that starts background work copies what it needs into memory it owns. What is shared across threads is the model, which is constant data, the data layer's handle on the developer's pool, and the context if the developer makes it shareable. The framework has no mutable global state.
- A read returns a fully materialized slice. Streaming results are reserved, not designed: nothing in this contract forbids a second result shape, but one would hold a connection past the call's return and want per-row memory, so it would own its resources and be the one result with a `deinit`.
