# Every read has a total order and states its bound; a cursor is plain sort values

A read action that returns many records must say how its result is bounded: either a `page` entry (the kinds of pagination it allows, a default limit and a maximum limit) or an explicit `.unbounded`. Leaving both out is a compile error. Every read is also totally ordered: when the sort is lowered the kernel appends the primary key attributes, ascending, to whatever sort was declared or supplied. A paged read returns a generated page struct instead of a slice, and under keyset pagination that page carries two cursors, one for its first record and one for its last. A cursor is the sort-term values of one record plus a fingerprint of the sort, encoded and not encrypted. We chose this because a read result is fully materialized in the caller's arena (ADR 0008), so the bound on a read is the bound on its memory and should never be an accident, and because a total order is what makes both kinds of pagination return stable pages without the developer having to think about ties.

## Considered Options

- **Pagination as an opt-in** (Ash's shape): a read with nothing declared returns everything. Rejected because the unbounded read is then the default and the one nobody chose. Requiring `.unbounded` costs one word where it is meant.
- **A sort term that holds any expression**: rejected in favour of a term that names an attribute or an expression calculation. Sorting by something computed, or by a value across a to-one relationship, means declaring an expression calculation first. This keeps a term small, makes a request sort trivially checkable, and gives every value in a cursor a name.
- **A tiebreak the action names itself** (Ash's `stable_sort`): rejected. The only gain is a narrower tiebreak column, and it adds a way to declare a tiebreak that is not unique. A meaningful default order is the job of the action's declared sort.
- **A cursor on every record** (Ash's shape, and what GraphQL Relay edges want): rejected for now. A record holds attributes only, so a per-record cursor needs a carrier, which is the loaded record (ADR 0012 reserves the name `cursor` in it), and it would be computed for every record of every keyset read when callers use the first and the last. It is reserved: a cursor depends only on one record's sort-term values and the sort, never on its position in a page, so a per-record cursor can be added without changing the encoding.
- **Encrypted cursors**: would let any value be sorted on without showing it to whoever holds the cursor. Rejected because it puts key management in the kernel. What may be sorted on under keyset pagination is restricted instead.
- **Keyset only, offset reserved**: rejected because offset costs one integer in the read operation once keyset is designed.
- **The keyset position written as expression nodes by the kernel**: rejected. The data layer lowers a position to its own SQL, since the correct predicate depends on null placement and mixed directions.

## Consequences

- A sort is an ordered list of terms. A term names an attribute or an expression calculation and one of four directions, which mean the same in every data layer: `asc` (nulls last), `desc` (nulls first), `asc_nulls_first`, `desc_nulls_last`. The defaults treat null as the largest value, as Postgres does, so a plain index serves them. A nulls variant on a term that cannot be null is a compile error. A function calculation as a term is a compile error (ADR 0010). Attribute names are typed by the compiler on the token; calculation names are checked when the model is lowered (ADR 0006).
- A read action may declare a sort. A sort supplied by the caller replaces it; nothing is merged. With neither, the order is the primary key's.
- The primary key is always appended, skipping attributes already in the sort. For a declared sort this is a build-time fact; for a caller's sort it happens at runtime.
- The `page` entry names the kinds allowed, keyset, offset or both, and when both are allowed the caller chooses per call. Default limit and maximum limit are both required; the kernel supplies no numbers. A call with no limit uses the default. A limit of zero or above the maximum is an invalid failure, never a silent clamp. Offset has no kernel maximum.
- A keyset call may pass `after` or `before`. `before` is lowered as the reversed sort and the kernel reverses the result, so records always come back in sort order.
- The page struct holds the records, `more` (whether more records exist in the direction travelled, found by fetching one record beyond the limit, with no second statement), `start` and `end` cursors on a keyset call, and a count when asked for. Its type is generated per action from the declaration and never varies per call. An unbounded read returns a bare slice, and a read declared to return one record returns an optional record and takes no page; it accepts a declared sort and a caller's sort, which decide which record is first. This amends ADR 0005, which said a read returns a slice.
- A count of all matching records is opt-in twice: the action declares `countable` and the caller asks per call. It is never computed otherwise.
- A cursor is a kernel type, opaque to the developer, with one encoding defined by the kernel; its bytes live in the scope's allocator with the rest of the result. The filter is not part of it, so a cursor may be used with a different filter. A cursor used under a different sort, or a malformed one, is an invalid failure.
- A sensitive attribute or calculation cannot be a sort term on a keyset call: a compile error when the sort is declared, an invalid failure when the caller supplies it. It may be sorted on with offset pagination or on an unbounded read.
- The caller's part of a read is one generated per-action value passed beside the input, with every field optional: filter, sort and page request. Fields the declaration does not allow are absent from the type (`page` on an unbounded action, `offset` when not allowed, `count` when not countable), so each misuse is a compiler error on the token, and `after`, `before` and `offset` are alternatives of one union. The input stays arguments only.
- The read operation the kernel hands the data layer gains the sort terms with the primary key appended, a limit, either an offset or a cursor position (decoded values and a direction), and a count flag. The data layer returns the sort-term values of the boundary records and the kernel encodes the cursors. Statement text for a declared sort is a build-time constant; for a caller's sort the same lowering writes it at runtime.
- Over HTTP the sort is one query parameter of comma-separated names with `-` for descending (`sort=-views,title`). It may name public attributes and public expression calculations that are not sensitive; nulls variants cannot be written in a request. Every such name is sortable by default, and the API surface has a per-action option to narrow the list or empty it. Callers inside the program are never narrowed.
- The page parameters are `limit`, `after`, `before`, `offset` and `count`, and only those the declaration allows exist. A read action exposed over HTTP with an argument of one of those names, or named `sort`, is a compile error from the surface. These six names are all the surface claims for sort and pagination; it reserves no prefix, and nothing here limits the query parameters another extension may add.
- A paged response is an object with `data` (the records) and `page` (`more`, `start` and `end` on a keyset call, `count` when asked for). Cursors are base64url text. There are no links to adjoining pages, in the body or in headers, since the surface does not know its public address.
- A keyset action exposed over HTTP whose declared sort has a term that is not public is a compile error from the surface that names the term, because the cursor would carry its values to the client.
- The OpenAPI description is derived with nothing hand-written: `sort` as an array of an enum of each sortable name and its `-` form, `limit` with the action's default and maximum, `after` and `before` as strings, `offset` as a non-negative integer, `count` as a boolean, and the response schema with its `page` object.
- A sort term names a calculation the way an expression does, so it must leave room for calculation arguments, which are reserved (ADR 0010).
- Amended (ADR 0015). A sort term must have a kind that is ordered: integer, float, decimal, text, instant, date or UUID. A boolean, bytes, enum, composite or list term is a compile error when the sort is declared and an invalid failure when a caller supplies it. The primary key the kernel appends is exempt: it only breaks ties, in whatever order the data layer gives its values. A calculation used as a sort term may read the context or `now`; a cursor still holds plain sort values, so a page boundary that moves because `now` moved between calls is the caller's concern.
