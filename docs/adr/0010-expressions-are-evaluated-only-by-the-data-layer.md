# Expressions are evaluated only by the data layer; a function calculation never enters an expression

A calculation has two forms. An expression calculation has an expression as its body and is evaluated by the data layer, inlined into the statement that needs it. A function calculation names a developer-written function that the kernel calls in the program after the data layer has returned. The kernel ships no evaluator for expressions: the data layer's lowering is the only thing that ever gives an expression a value. A function calculation is therefore opaque to every expression, and referencing one in a filter, a sort, a policy condition, a change or another calculation's body is a compile error when the model is lowered. We chose this because it keeps one meaning for every expression and keeps the shape of every query a build-time fact (ADR 0005): nothing is filtered, sorted or computed in memory because of what a call happened to reference.

## Considered Options

- **An in-memory evaluator in the kernel beside the data layer's lowering** (Ash's shape): an expression can then be computed for a record already in hand, for a resource with no data layer, and as a fallback when a function calculation appears in a filter. Rejected because it is a second implementation of the expression language that must agree with Postgres on null handling, text comparison and collation, and decimal arithmetic, and every disagreement is a wrong result rather than an error. It also brings back the behaviour this design removes: a filter that silently runs in the program over records already fetched.
- **Function calculations usable in expressions, evaluated in memory after the read**: rejected for the same reason, and because it breaks pagination and sort, which the data layer has already applied before the function runs.
- **Expression calculations only**: rejected because a value that needs program code (formatting with a library, a call to another service) would have no place in the model, and every API surface would have to be told about it separately.

## Consequences

- A calculation is an entry in the `calculations` list of the `resource` declaration, with a name, a stated type, and either an expression or a function named by declaration name (ADR 0003). The type is always written, never inferred: it is what lets the compiler type the body on the exact token and what generated source needs.
- The type is an attribute type (ADR 0007). It must equal the checker's result kind for the body exactly, optionality included; there is no implicit widening. A value type is allowed when the body's kind matches its storage, and its constraints are not enforced on computed values.
- An expression calculation may be used wherever an expression may: filters, sorts, policy conditions, changes, other calculations' bodies, and request filters subject to its `public` flag. Its body may read attributes, other expression calculations, and related records through the two relationship nodes of ADR 0006; it may not read an action's arguments, since a calculation belongs to the resource. A calculation that references itself, directly or through others, is a compile error.
- A resource with no data layer may declare function calculations only.
- A function calculation has two accepted shapes, told apart by the function's signature: one record in and one value out, or a slice of records in and a slice of values out. The kernel wraps the first in a loop, so it only ever calls the second. A function of neither shape is a compile error that names both. The second shape exists so that a calculation doing I/O does it once per call rather than once per record.
- A function calculation receives the scope and the context (ADR 0008), may fail with the shared error set (ADR 0009), and a failure fails the whole action call with the calculation recorded as its origin. It sees the record's attributes only; how it declares a dependency on another calculation or on related records is decided with how loaded data is carried.
- A calculation is computed only when asked for, by a load request or by a reference inside an expression. There is no flag that computes one on every read.
- The names of a resource's attributes, calculations and relationships are unique within the resource; a clash is a compile error. Results and API surfaces show them side by side, and aggregates, which are reserved, join the same names later.
- A calculation carries the `public` and `sensitive` flags of an attribute, both false by default. A public calculation may read attributes that are not public. An expression calculation whose body reads a sensitive attribute must state `sensitive` explicitly, true or false, or it is a compile error; a function calculation's flags are taken as written.
- Calculations take no arguments. This is reserved rather than designed: the node that references a calculation and the shape of a load request must leave room for bound argument values.
- The first thing to revisit, if real use strains it, is computing an expression calculation for a record that did not come from a read, which today costs a round trip to the data layer.
