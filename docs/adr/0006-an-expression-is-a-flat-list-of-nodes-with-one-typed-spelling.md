# An expression is a flat list of nodes, written in one compiler-typed spelling

An expression is plain data: a list of nodes in prefix order, with no Zig types in it and no pointers between nodes. One checker types it against the model and one lowering in the data layer turns it into parameterised SQL; both are ordinary functions that run unchanged at build time, on expressions written in a declaration, and at runtime, on expressions written at a call site or built from a request. A developer writes an expression in exactly one spelling, prefix constructors on a type that carries the resource and the result type (`.all(&.{ .eq(.status, .value(.published)), .gt(.views, .arg(.min_views)) })`), which the compiler types on the exact token and which produces the node list. We chose this because one representation then serves every place an expression appears (filter, calculation body, atomic update, request filter) without an allocator, and because the spelling keeps the feedback loop the design answers to: a compiler error on the developer's token.

Measured on the prototype branch `prototype/expression-language` (Zig 0.17.1): one filter in three spellings, 28 mistakes, plus relationship crossing written both ways.

## Considered Options

- **A tree of nodes joined by pointers**: the familiar shape. Rejected because a tree built by functions at a call site with runtime values points into dead stack frames, so it needs an allocator or a second builder for runtime use. The flat list is built by value on the stack and is the same value in the model.
- **Methods on attribute handles** (`p.attr(.views).gt(...).andAlso(...)`): the same compiler typing as the chosen spelling. Rejected because it needs a handle constant in every resource, cannot use `and` and `or` (keywords), has no precedence, and still falls back to prefix constructors for `not` and relationship crossing; it is the longest spelling once an expression has more than two comparisons.
- **A string parsed at comptime** (`"status == 'published' and views > $min_views"`): reads best. Rejected because nothing in it is typed by the compiler: every mistake is reported from framework code with the developer's file absent, and a syntax error is an offset into a string. It remains addable later as another way to produce the same node list.
- **Crossing a relationship without naming the destination** (`.exists(.comments, ...)`): shorter. Rejected because everything written past the relationship then loses compiler typing: a misspelled attribute or a literal of the wrong type on the far side is reported from framework code instead of on the token.

## Consequences

- There are six kinds of node: a reference to an attribute or calculation, an argument, a value, a call of an operator with its operand count, a test for the existence of related records over a to-many relationship, and a read through a to-one relationship. Values are data, so an expression is the same whether its values were known at build time or arrived at runtime.
- The checker returns the result kind of an expression or a message. For a declared expression it runs when the model is lowered and its message is a compile error; for a request it runs at runtime and its message is the rejection. A request filter is therefore checked by the same code as the build.
- The data layer's statement text for a declared expression is a build-time constant. For an expression built at runtime the same lowering writes the text at runtime. No value enters statement text in either case: every literal and every argument is a bound parameter.
- A calculation is referenced by name in an expression and inlined when lowered.
- A comparison has two forms: attribute on the left, where the right side is typed from the attribute, and a general form that states the type, because the compiler cannot infer the type of a left operand written as a constructor.
- Crossing a relationship names the destination resource by type (`.exists(Comment, .comments, ...)`). The named type only drives compiler typing; the checker and the lowering use the relationship's destination from the model, so a wrong name cannot produce a wrong statement. The node records the named destination and the checker reports a mismatch.
- Three kinds of name cannot be typed on the token inside a declaration: arguments, calculations and relationships. They are part of the declaration the expression is written inside, and reading it from there is a dependency loop. They are checked when the model is lowered, with a message naming the resource, the action and the mistake, and no location in the developer's file. This is the same weakest error ADR 0001 accepts.
- Typing these names by declaring an action differently was prototyped and rejected (branch `prototype/argument-typing`, Zig 0.17.1). Two shapes put a misspelled argument on the token: an action written as a function call that takes its arguments as a struct type (`.read("popular", struct { min_views: i64 }, .{ ... })`), and an arguments struct declared outside the declaration and named at each argument (`.argOf(PopularArguments, .min_views)`). Both were rejected because they make the action entry worse to write and read: the entry keeps its argument list and the weaker error is accepted. The same move reaches calculation and relationship names only by moving them out of the `resource` declaration into sibling declarations, and is not taken for the same reason. A better location for these errors is still wanted, from a change that leaves the declaration as it is.
- An attribute compared with an attribute of another type is a framework compile error whose notes include the developer's token, not a compiler error on it.
- An expression has a fixed maximum number of nodes. Exceeding it is a compile error in a declaration and a rejected request at runtime.
- The method spelling is not provided. The string spelling is not provided and nothing prevents adding it.
