# Extensions are registered at the domain root and take their options inside the declaration

An extension is a Zig namespace that satisfies a small contract, listed once at the domain root beside the resources. The kernel derives from that list an `extensions` block inside every `resource` declaration, with one entry per registered extension, keyed by the extension's name and typed by the extension's own options type. The extension normalizes its options to plain data of its own, and contributes in the three ways ADR 0003 allows: comptime code, descriptions, and commands. The kernel never names an extension. We chose this because it gives an extension's options the same compiler errors as the kernel's own, on the exact token, without anyone writing a check: a misspelled option, a misspelled attribute, a misspelled extension name and an extension that was never registered are all ordinary "no field named" errors in the developer's file.

Measured on the prototype branch `prototype/extension-mechanism` (Zig 0.17.0): one extension, fifteen mistakes.

## Considered Options

- **Sibling declaration on the resource** (`pub const postgres = postgres.Options(@This()){ ... }`, found by name): keeps the kernel's options type independent of the extension list. Rejected because a declaration named after the extension makes the import ambiguous inside the struct (`error: ambiguous reference`), and a misspelled declaration name is silently ignored, so the resource quietly loses its options. Finding the declaration by type instead of by name would resolve the signatures of developer-written functions, which may mention generated source that does not exist yet.
- **Extension options for an attribute merged into the kernel's per-attribute block** (`.email = .{ .unique = true, .postgres = .{ ... } }`): everything about one attribute in one place. Rejected because an extension would then supply two option types that the kernel weaves into two derived blocks; with its own block the extension owns one options type whole. The cost is that an attribute's metadata is spread over one block per extension.
- **Registration in `build.zig`**: rejected because the build script cannot be read by comptime code, so the list would have to be stated twice. The domain root already states the closed world.
- **Described types and functions namespaced by extension** (`api.Author.postgres.get`): no collisions possible. Rejected for the shorter call site that does not make the developer name the provider at every call; a collision is a compile error instead.
- **A named build step per command** (`zig build migrate`): reads better, but the build script cannot read the domain at configure time, so each name would be repeated in `build.zig` and a typo there would be a runtime error.

## Consequences

- The contract is: a name; an options type per resource; a plain-data type the options normalize to; a function that normalizes and validates; and, optionally, descriptions per resource, text for an action's doc comment, and commands. Any comptime code, including another extension, can ask for an extension's normalized options for a resource.
- The name is the key in the `extensions` block and the import name in generated source, so it is unique in a build.
- An extension's per-attribute options are a block of its own, keyed by field name, built with a public kernel helper. A misspelled attribute is an exact compiler error there too.
- A resource that gives an extension no options is not an error in the kernel. The extension decides what absence means; for a data layer it means the resource is not persisted.
- The table name is a data-layer option, not a kernel option (ADR 0001 amended).
- An extension's own rules (two attributes mapped to one column, a type with no mapping) are reported from the extension, naming the resource and attribute in the message. The developer's file does not appear. This is the same weakest error ADR 0001 accepts for the kernel.
- The model has one form. It is plain data with no types in it, so the value comptime code reads is the value a command reads at runtime; lowering does not produce two. Comptime code that needs a type takes the resource's struct beside the model. An extension's normalized options must be plain data for the same reason.
- A description is a struct, an enum, or a function. A type inside one is either an existing type, passed as a type and spelled by the emitter (primitives, optionals, constant slices, records, public declarations of the extension), or the name of another description of the same extension on the same resource. A type the emitter cannot spell is a compile error naming the extension and the description. Unions, methods, generic functions and default values are not describable until a derivation needs them.
- A described function names the comptime function it delegates to as one of the extension's own declarations, so a misspelling is an exact compiler error in the extension's source. The emitter writes the call with the resource first and the parameters after it.
- Described types and functions sit directly on the resource in generated source, beside the kernel's. The kernel rejects a name described twice on one resource, naming both providers. A resource cannot have an action whose name an extension also describes.
- The emitter checks descriptions before writing: a reference to a description that does not exist, and a delegate whose signature disagrees with its description, are reported against the extension. Unchecked, both surface only as errors inside generated source.
- Commands need no registration beyond being declared by a registered extension. The kernel provides one runner, built from the domain without generated source, and one build step: `zig build zava -- <extension>.<command> <arguments>`; with no arguments it lists the commands. A developer who wants a shorter name adds their own step.
- A command receives I/O, an allocator, the model, its extension's normalized options for every resource, and its arguments. Whether it may hand Zig data back to the program stays closed (ADR 0003).
- The type of the `extensions` block is derived from the registered list, so the kernel module reads the domain root.
- The anonymous literal (`.postgres = .{ ... }`) is the only documented spelling of an entry, at both levels. Measured on ZLS 0.17.0, it gets no completion, hover or go-to-definition, and extension names never complete in any spelling. Writing the entry with the extension's named type (`.postgres = postgres.Options(@This()){ ... }`) restores them for the top-level option names, but it is longer, repeats `@This()` and makes every resource file import the extension, so it is not the documented form: it is valid, not forbidden, and mentioned once under editor support as an opt-in. The contract does not require an extension to publish its per-attribute options type; extension authors are advised to keep option types public and hand-written where they can, which lets a developer who opts in name the nested entry too. The gap is accepted with no revisit trigger: it closes without a change here once the language server gets types from the compiler.
- The contract gains one optional part: an options type per value type. The kernel derives from the registered list an `extensions` block inside every value type's declaration, keyed and typed the same way as the block inside a `resource` declaration, so an extension can be told once how to map a type instead of at every attribute that uses it (ADR 0007).
