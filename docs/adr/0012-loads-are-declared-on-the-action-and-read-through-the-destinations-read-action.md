# Loads are declared on the action and read through the destination's read action

What an action returns with each record beyond its attributes, calculations and related records, is declared on the action in a `load` block and nowhere else: a caller cannot ask for a load per call. The action then returns a loaded record, a struct generated per action that holds the record and each loaded name as a plain field, so there is no "not loaded" state anywhere in the program. A related record is never fetched directly: each relationship entry in a load names a read action on the destination, and that action's filter, sort, bound and own loads apply, so nesting is composition of actions rather than a tree written at the call site. We chose this because it keeps the shape of every query a build-time fact (ADR 0005), keeps every type a developer codes against as source (ADR 0003), holds to the principle that every read goes through a named action, and removes the most reported runtime surprise in Ash: a value that was never loaded reaching the code that uses it.

## Considered Options

- **A load supplied per call, in a result type with a slot per loadable name** (Ash's shape): one action serves every shape. Rejected because every slot is then loaded-or-not at runtime, a to-one relationship that may also be null needs two layers of optionality, the statement text is no longer a constant, and the response schema of an operation is no longer exact.
- **A load supplied per call, with a result type that follows it**: the type would have to be built from a comptime value with `@Struct`, which ADR 0003 rules out and the language server cannot see.
- **Declared loads with entries a caller may switch on per call**: the type stays fixed per action, with the switchable entries as optional fields. Not designed. It only adds fields and a flag on an entry, so it stays addable, and it is the first thing to revisit if real use shows one action per shape to be too many: the cost of this decision grows with the number of independent loads an application wants to combine freely, which is the territory of a GraphQL surface.
- **Related records read by the data layer straight from the relationship, with no action**: shorter to declare. Rejected because it is a read that bypasses an action, which leaves nothing for authorization to hang on, and because filtering, sorting and bounding a load would each need a second spelling beside the one read actions already have.
- **An implicit default read action per resource** (Ash's primary read): rejected. The kernel has no primary action; the default is stated on the relationship instead, where it is visible.
- **Loaded names nested under a `loaded` field**, or **a generated struct that copies the attributes beside the loaded names**: the first reserves no names but lengthens every access; the second stops a loaded record from being passed to a function that takes the record. Rejected for the record beside the loaded names in one struct.

## Consequences

- A `load` block is keyed by name, and every entry is a struct. A calculation entry is empty (`.word_count = .{}`), which is the room calculation arguments need (reserved by ADR 0010). A relationship entry may name the destination's read action and give it argument values (`.comments = .{ .read = .list_visible, .args = .{ ... } }`).
- A relationship declaration may name a default read action. A load entry that names none uses it, and a relationship loaded with neither is a compile error. There is no other default.
- Argument values in a load entry are literals. Binding an argument from the parent record or from the caller is not designed. An action named by a load must have no required argument left unbound.
- The field for a loaded relationship has exactly the type the named action returns. A to-one relationship needs an action that returns one record, and the field is an optional, always, because the action's filter, and later its policy, may hide the record. A to-many relationship needs an action that returns many: an unbounded action gives a slice, and a paged action gives its page struct for each parent, holding the first page at the default limit with `more` and its cursors and no count. The caller reads further pages by calling that action directly with the cursor and a filter on the parent, which ADR 0011 already allows. A mismatch of kind is a compile error. The bound on a to-many load is therefore never an accident: the destination action has already stated it.
- Nesting comes from the named action's own loads. A cycle through actions is a compile error.
- The named action's steps run once per load, not once per parent, with the same context and scope; a failure fails the whole call with that action as its origin (ADR 0009).
- A loaded record is `struct { record: T, <loaded names> }`, generated per action and named after it. An action that loads nothing returns the bare record, as before. `record` and `cursor` may not be used as the name of a calculation or relationship: the second is reserved so that a cursor per record (reserved by ADR 0011) has a place to ride without a breaking change.
- The loads of an action that returns many, paged or not, apply to every record alike. A related record reached from several parents is repeated by value. Everything is allocated in the scope's allocator (ADR 0008).
- A create or an update may declare loads, with the same block and the same result. The kernel reads them after the steps of the `after` phase, inside the transaction, so the result reflects those steps; a data layer is free to fold the read into the write statement. A destroy and a generic action declare none.
- A function calculation states what it depends on with its own `load` block, in the same form. Its function then takes the generated loaded record, one or a slice of them (ADR 0010), instead of the bare record. The kernel loads the dependencies before the call; they do not appear in the action's result unless the action loads them too, and anything needed more than once is computed once. A function calculation may depend on another; a cycle is a compile error.
- The kernel hands the data layer the whole tree in one read operation. Each node carries the relationship, the named action's lowered read (filter, sort, limit, bound arguments) and the expression calculations to compute. The data layer returns the tree filled, and whether it joins or issues follow-up statements is its own choice; a per-parent limit costs it a lateral join or a window function. The kernel then runs function calculations from the leaves up. The tree is a build-time constant, so the statement text is too.
- The statements of one read are not promised a common snapshot unless the call is already inside a transaction. A write's loads are read inside its transaction.
- A many-to-many load applies the destination's action to the destination records. Join resource records are crossed and never returned, and no action of the join resource is involved; whether its policies should gate the crossing is decided with authorization. To load the join records themselves, declare a has-many relationship to the join resource and load that.
- The query (ADR 0011) stays a filter, a sort and a page request. This amends the expectation recorded there that a per-call load would join it.
- Over HTTP a loaded record is one flat object: public attributes and loaded names side by side, with no `record` key, which the uniqueness of names (ADR 0010) makes safe. A loaded relationship nests the named action's encoding. A loaded calculation that is not public is left out, like an attribute that is not public. A relationship has no `public` flag: exposing an action that declares the load is the consent. The response schema of each operation is derived exactly from the tree.
- There is no way to load onto a record already in hand; the route is to call a read action. This is the same round trip ADR 0010 names for an expression calculation.
- Aggregates, which are reserved, join the same names and would be load entries of the same form. Streaming read results, also reserved, would have to say how loaded data arrives per row; nothing here assumes they exist.
